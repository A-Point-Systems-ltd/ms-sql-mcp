# Changelog

## Unreleased

- New extension-only tool `language_service` (T-SQL IntelliSense), registered and routed only when `MSSQL_SCRIPT_RUNNER=true` (26 tools then; the agent tool count stays 23). Actions `completion`, `hover`, `signatureHelp`, `warm`, `refresh`, built on Microsoft SqlParser 180.9.0 with SMO / SmoMetadataProvider 181.37.1 through a completion wrapper ported from microsoft/sqltoolsservice (MIT). Procedure parameters after `EXEC proc` are added from the parser's method help (named and leading positional arguments already given are skipped). One metadata cache per connection and database, 2-second binding timeout with a keyword fallback (`cacheState: "loading"`), dropped on connection close / removal, `refresh` and 30 minutes idle. Read-only; logs counts only. SqlParser is under the SMO licence terms: see `THIRD-PARTY-NOTICES.txt` and README, "IntelliSense (extension only)". The single-file exe grows by about 5.5 MB.
- `ConnectionRegistry` raises a `Changed` event when a connection is closed, removed or (ad hoc) replaced.

- The `DDL_Audit` trigger script (shared by `install_insights_layer` and `ddl_history install`, one install routine) is hardened so it never blocks another principal's DDL: it runs `WITH EXECUTE AS 'DDL_Audit_Writer'`, a loginless user the install creates (`WITHOUT LOGIN`, default schema dbo) with only `INSERT, SELECT ON dbo.DDL_AuditLog` (a `db_ddladmin`-only login no longer gets error 229, a database with an orphaned dbo keeps working, and nothing run inside the insert gets more rights); it skips the insert while `dbo.DDL_AuditLog` has any DML trigger; it forces the SET options its xml methods need (no more error 1934 for `ANSI_WARNINGS` / `CONCAT_NULL_YIELDS_NULL` OFF sessions); it records `ORIGINAL_LOGIN()`; and it wraps the insert and the "last modified" message in `TRY ... CATCH` with `XACT_ABORT OFF`, so a failed insert lets the DDL commit unlogged. A principal named `DDL_Audit_Writer` that is not a loginless SQL user is refused. Install checks the new user's context with a pre-flight `EXECUTE AS USER` and, on any failure of the trigger step, drops the user and the table it created. Existing triggers are never altered. Rollback: `DROP TRIGGER [DDL_Audit] ON DATABASE; DROP USER [DDL_Audit_Writer];`. See README, "DDL history (extension only)".
- `ddl_history` audit IDs are 64-bit (`get` takes a `long` id; list/get read `bigint` IDs).
- An existing loginless `DDL_Audit_Writer` with more rights than INSERT/SELECT on `dbo.DDL_AuditLog` (a role membership, an owned schema or another granted permission) is refused, and nothing on it is changed. `ddl_history status` runs the same check: `canInstall` false and the reason in `warnings`. It also returns `loggingSuppressed: true` while `dbo.DDL_AuditLog` has DML triggers.
- `ddl_history` checks an existing `dbo.DDL_AuditLog` by type and width: the name columns must be `varchar` / `nvarchar` of at least 100 characters (`EventType` 64), `CommandText` `nvarchar(max)` or `varchar(max)` (the latter with a lossy-text warning in `status.warnings`), `CommandXML` `xml`, none of them computed or identity, and `ID` (integer) and `PostTime` (date/time) must exist. The error lists every problem.
- `ddl_history status` also returns `serverName` (`@@SERVERNAME`) and `databaseName` (`DB_NAME()`).
- A `dbo.DDL_AuditLog` created by `ddl_history install` gets the index `IX_DDL_AuditLog_ObjectName` (`ObjectName`, `ID`, including `SchemaName`, `LoginName`, `PostTime`). Existing tables are not changed.
- Console log level precedence: `MSSQL_CONSOLE_LOG_LEVEL` when set, otherwise `Logging:Console:LogLevel:Default` / `Logging:LogLevel:Default` from the standard configuration (appsettings or `Logging__*` env), otherwise `Warning`. An invalid `MSSQL_CONSOLE_LOG_LEVEL` is now ignored with one warning line instead of forcing `Warning`.
- Console logging is quieter: the stderr console logger now defaults to `Warning` (it was `Information`), because clients such as Cursor show every stderr line as `[error]`. `MSSQL_CONSOLE_LOG_LEVEL` (`Trace`, `Debug`, `Information`, `Warning`, `Error`, `Critical`, `None`) sets another level; an invalid value falls back to `Warning` with one warning line. `FATAL:` startup messages and the `LOG_FILE_PATH` log are unchanged.
- New extension-only tool `ddl_history`, registered and routed only when `MSSQL_SCRIPT_RUNNER=true` (the agent tool count stays 23). `status` reports whether `dbo.DDL_AuditLog` and the `DDL_Audit` database trigger exist; `install` creates whichever is missing (never altering, dropping or enabling an existing one; refused on read-only connections; an existing table the trigger cannot insert into blocks the install and is reported as `tableCompatible: false`); `list` returns an object's DDL events newest first and `get` returns one event's command text. See README, "DDL history (extension only)".
- `run_script` hardening (extension-only tool; agent tools unchanged):
  - Each run uses a new, unpooled session (`Pooling=false`), so session settings from one query window (isolation level, `sp_setapprole`, `EXECUTE AS`) no longer leak into the next.
  - Size caps, all of which let the script run to the end: 10000 messages per run (later `info` / `rows` messages dropped), 1000 errors (then only the most recent error is kept, in one slot), 200 result sets (later sets drained, not returned), about 32 MB of cell data and message text per run (later rows counted only, later `info` / `rows` messages dropped; errors and warnings still kept), string cells cut at 65536 characters and binary cells at 32768 bytes (with a `… (truncated, N chars|bytes)` suffix), and `GO n` with n above 10000 refused for that batch. Each cap adds one `warning`. A `GO` count too large for an integer is now a separator (and hits the cap) instead of being sent to the server.
  - Exact values: `decimal`, `numeric`, `money`, `smallmoney` and `bigint` outside +/-2^53 are returned as invariant strings instead of JSON numbers that the extension rounded; binary values are `0x` + uppercase hex instead of base64.
  - Read-only refusals in the editor give a short reason and no longer tell the user to use `read_data` / `execute_sql`. The agent tools' messages are unchanged.
  - Cancellation via `notifications/cancelled` is covered end to end by a protocol test (row rolled back, locks released, server still serving).
- `script_object` has an optional `form` parameter (`create` default, or `alter`). `form: "alter"` returns views, stored procedures, functions and triggers as `CREATE OR ALTER` (SQL Server 2016 SP1+ / Azure) or `ALTER` (older), ready to edit and re-run; an indexed view gets a warning (and a `-- WARNING` comment) that altering it drops its indexes, which the index statements in the script recreate. Other object types with `form: "alter"` and unknown `form` values return an error.
- New extension-only tool `run_script`, registered only when `MSSQL_SCRIPT_RUNNER=true` (not listed to agents; the agent tool count stays 23). It runs a multi-batch T-SQL script with SSMS-style `GO` / `GO n` separators on one session and returns every result set (row cap per set, total row count) and every message (PRINT, row counts, errors with script line numbers). At most 50000 rows are kept per run across all result sets. Read-only connections run only single read-only `SELECT` batches, each inside a rolled-back transaction (comment-only batches are skipped); a transaction left open on a read/write connection is rolled back with a warning. See README, "Script runner (extension only)".
- Connection-string `${env:NAME}` placeholders enclosed in double quotes (`Password="${env:X}"`) now have any `"` in the substituted value doubled, so passwords containing `;`, `=` or `"` work. Unquoted placeholders are substituted raw, as before. See README, "Multiple connections".
- Single-quoted placeholders (`Password='${env:X}'`) now have any `'` in the substituted value doubled, the same way.
- Read-only connections make no writes at all: the AI Insights layer no longer creates baselines, archives stale insights or runs DDL processing on a read-only connection (cached insights are still returned).
- Ad-hoc connections (`open_connection` with a connection string) are hardened: Integrated Security / Active Directory authentication needs `MSSQL_ADHOC_ALLOW_INTEGRATED_AUTH=true`, `readOnly=false` needs `MSSQL_ADHOC_ALLOW_WRITE=true`, `MSSQL_ADHOC_ALLOWED_HOSTS` can limit target hosts, `AttachDBFilename` and `User Instance` are always refused, and a failed connection test returns a generic message (details go to the log, masked). Replacing an ad-hoc entry clears its old connection pool.
- `script_object` fidelity: disabled triggers are scripted followed by `DISABLE TRIGGER` (with a warning); `IGNORE_DUP_KEY = ON`, `NOT FOR REPLICATION` on identity columns and CHECK constraints, and non-default filegroups (`ON [fg]`) are scripted; Azure SQL Database / Managed Instance (EngineEdition 5 / 8) use `CREATE OR ALTER` and read temporal / memory-optimized metadata.
- Ad-hoc connection strings with `Failover Partner` are always refused (the failover host would bypass `MSSQL_ADHOC_ALLOWED_HOSTS`).
- `script_object` emits `TEXTIMAGE_ON [fg]` when a table's LOB data lives on a filegroup other than the one it would use by default.
- `describe_view` / `describe_table` index key lists no longer XML-escape column names (`a&b` instead of `a&amp;b`).
- An unknown tool name now gets the MCP unknown-tool error instead of a "'connection' argument is required" error in multi-connection mode.
- Server `<Version>` is now set in `MssqlMcp.csproj` (1.0.0); assembly, file and informational versions derive from it and must match the VS Code extension version (enforced by CI).
